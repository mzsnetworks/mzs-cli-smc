# LinkedIn — what-survives-you


Did your last outage change a document, or change a default? Only one of those is still working in two years.

Both feel like closure on the day. The postmortem gets written, the finding is clear, somebody updates the runbook, and the item is closed. Genuinely good work, and the organization has learned something.

Then the people who were on that call move on. Not dramatically — one changes teams, one leaves, one is still there but has run forty incidents since and the details have blurred. The document is exactly where it was. Nobody opens it, because opening it requires already suspecting the thing it warns about.

That is the whole difference. A document transmits a lesson only to someone who goes looking for it. A default enforces it on someone who never heard the story.

The defaults are specific and usually small. A field added to the change template so the question gets asked every time. A validation step that fails on the condition that caused it. A monitoring check for the state that was invisible. A changed standard, so the next site built does not inherit the thing you spent a night on.

None of those require anyone to remember anything, which is the point.

So I ask a blunt question at the end of a postmortem now. If everybody in this room left tomorrow, what would still stop this happening again? If the answer is a document, we have recorded the incident rather than fixed it.

Write the document too. It carries the reasoning, and the reasoning is what lets a future engineer change the default safely rather than deleting it as mysterious.

But the test is survival. A lesson that depends on somebody remembering it is already on its way out of the organization.

What did your last postmortem actually change?
